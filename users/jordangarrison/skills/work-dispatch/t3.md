# T3 Code dispatch

Use the active session's T3 instructions and discover tool schemas before
calling them. This file defines workflow intent, not a duplicate API contract.

## Dedicated placement

For delegated work, use T3's delegation mechanism when its rules call for it.
Discover capabilities before the first delegation, honor requested staffing,
and use runtime-managed isolation for separate checkouts. Never create a shell
worktree and assume that it binds a T3 child to the checkout.

A request for a dedicated ticket subthread calls for an accessible T3-managed
workstream. Inspect the supported child controls and explain any steering gap.
A new **top-level thread** is different: launch one only when the user asks for
a new thread, using the tool's workspace strategy for checkout binding. A
request for a subagent or parallel work alone is not that authorization.

Native harness helpers remain available under the session's tool-selection
rules. Do not replace them all with T3 threads merely because T3 owns the run.

## Context and supervision

Pass a self-contained brief; do not assume parent history or local files are
visible. Include the owner, parent reference, decisions, scope, and report
contract. For remote workers, use supported environment and artifact delivery.
Return the exact thread link supplied by the tool so the user can reach it.

Follow the returned lifecycle instructions. Use completion notifications;
do not poll running delegates or install a parallel watcher for them. Read a
thread before answering questions about its current state. Use the supported
cancel operation for work no longer needed.

Follow-up reviews, steering, and continuation must use the operations permitted
for that worker type; do not assume top-level thread messaging can control a
delegate. If the requested steering is unsupported, disclose it before launch
and ask about an appropriate dedicated thread or cross-runtime handoff.
